# Competition-readiness backlog

Scope: the reusable FRC platform needed to build robot logic reliably: actuation safety, transport, runtime/API contracts, sensing, deployment and diagnostics. Game strategy, shot timing, mechanism coordination rules and additional autonomous routines are not readiness requirements here.

This is an **open-work list**, not a changelog. Completed work and its reasoning remain in `git log`. Remove an item only after its acceptance check passes; a passing existing suite does not close a newly identified coverage gap. Physical acceptance follows [docs/BRINGUP.md](docs/BRINGUP.md).

## Unresolved incidents — investigate, do not declare fixed by a rerun

- [ ] **INC-2 — Confirm the Phoenix simulator stall fix in CI.** **Cause established.** Phoenix's desktop simulator serves every simulated device from one thread, which also rewrites each device's `ctre_sim/*.dat` in the working directory on every config write. While Gradle wrote the other build variant to the same disk, a rewrite blocked that thread for up to hundreds of milliseconds: configure requests failed (TxFailed/RxTimeout), feedback went stale and `Configure()` left devices unavailable (CI runs 42718398981, 42762211224, 42769978513, 42775301670). A disk write load reproduces this locally; the same load with that directory in RAM does not. `PhoenixBackend_test` now keeps simulator state in a fresh `/dev/shm` directory and bounds each wait for configured, fresh, neutral devices (`AwaitReady`, whose failure names each device and its state). Close once CI runs that include the fix pass the RIO adapter job; an `AwaitReady` failure there is a recurrence. Linux success does not establish macOS SDK/toolchain readiness. On macOS the Phoenix simulator thread also stalls without disk load when the host CPU is loaded: at load 10–44 on 12 cores the enabled sim showed 1–4 all-device feedback stalls per second (50–260 ms), and `phoenixTest` failed 4 of 8 runs with `ctre_sim` on disk and 6 of 8 on a RAM disk. A RAM directory does not fix macOS; treat macOS `phoenixTest` failures under load as this, and close INC-2 on Linux CI as stated.
- [ ] **INC-3 — Critical-node restart latency on macOS.** **Incident.** In the macOS rerun of CI run 42720554711 (job 129517143967), `match_rehearsal_test` failed: the SIGKILLed drivetrain restarted (restart_count 1) but sent no `/hw/request/drivetrain` within the 300 ms the driver stays frozen, so the stale-lane check had nothing to examine. Linux runs pass; the Linux per-stage SIGKILL-to-first-request breakdown, idle and under a disk write load, is in [restart latency](talOS/launcher/README.md#restart-latency). The macOS cause is not established: the deployment host is a Mac mini, so measure those stages there, also while nodes write their event logs to the same disk (`tools/mac_qualify.sh` runs `//talOS/launcher:restart_latency` idle and with `--disk-load 8`), before widening the window; the frozen producer must stay below the 500 ms stall floor.
- [ ] **INC-5 — Confirm the cause of probes exiting 127 on macOS.** **Incident; cause probable, not confirmed.** macOS CI runs 42785663001 (`supervision_test`, `alpha`) and 42720554711 (`graph_test`, `front_left_camera`) failed a `--describe` probe with exit 127 and no message. The probable cause is the child's guardian fork refused with `EAGAIN` at the per-user process limit while the probes run in parallel (reproduced under `RLIMIT_NPROC`); that path then exited 127 silently. A probe now retries a fork refused with `EAGAIN` or `ENOMEM` until the describe deadline, and every other child failure names its step and errno. A probe that spawns only after a retry prints `[launcher] probe of <binary> spawned on attempt N (after <step>: <errno>)`. Confirm from a macOS CI log, either that line or a failed probe naming `fork (guardian)` or `fork` (with the process counts the build-macos failure step records), that the process limit is the cause; a probe failure naming another step, or an exit 127 without a named step, means it is not. Close after that confirmation; a passing rerun without the line is not evidence.
- [ ] **INC-6 — Hardware-request output gaps above 30 ms on macOS CI.** **Incident; cause unknown.** `startup_test` and `match_rehearsal_test` require recorded `/hw/request` (or bridge `/hw/command`) rows at most 30 ms apart inside checked windows. macOS CI runs 42775301670 (gaps 43.8 and 46.9 ms) and 42796457757 (39.5 and 38.7 ms) failed it; Linux runs and other macOS runs pass. Requests are due every 5 ms and the command timeout is 100 ms, so these gaps are not unsafe, but whether ticks or their recording were late on that host is not established. On the robot the bridge now holds a late owner's demand up to its owner timeout (50 ms for these subsystems), so gaps like these no longer brake the drivetrain, but a gap past 50 ms still neutralizes it. Measure per-node loop lateness on the Mac mini (FIELD-3) before treating it as runner noise; do not widen the 30 ms bound without that evidence. Candidate cause: a node print blocking on its output file under disk load stalled the driver 255 ms on the Mac mini; the launcher now drains node output on its own threads (LOG-4), so the next macOS CI runs show whether the gaps recur.

## Physical and deployment qualification gates

These are separate from software fixes, not evidence that a failure already exists. Agents must not change physical CAN IDs or set `commissioned = true`.

Use the one-Kraken bench ([docs/BENCH.md](docs/BENCH.md), config `bench/`) for link/stop/timing qualification before the robot exists; it cannot qualify a full CAN bus, cameras or the drivetrain. Run `session_report --strict` on bench sessions; `NOT MEASURED` is not a pass.

- [ ] **FIELD-1 — Network, electrical configuration and commissioning.** Verify coprocessor/RIO addressing, field bundle selection, CAN IDs, encoder offsets, inversion and controller limits against the real robot. A responsible human commissions only after restrained disabled/enable tests; update configuration golden checks alongside deliberate hardware changes.
- [ ] **FIELD-2 — Independent stop and fault measurements.** Measure DS disable/e-stop, companion stop/stall, Ethernet removal, RIO cold reboot, single Talon/CANcoder loss and total bus loss. Confirm affected-output/dependency isolation and safe fresh recovery. Measure voltage/current or independent motion/power evidence, not merely requested neutral or invalid feedback. Include PWM zero versus pulse-loss behavior and persisted-config boot restoration.
- [ ] **FIELD-3 — Full-bus load and realtime tails.** On the actual coprocessor/RIO, record CAN utilization, per-signal ages, hardware gaps, command latency, loop lateness, callback duration and watchdog crossings under intended load, Python GC, disabled neutral refresh and reset restoration. Qualify achieved signal rates rather than assuming the requested rates. Desktop measurements are not Mini acceptance evidence; callback duration differs from dispatch lateness.
- [ ] **FIELD-4 — Camera qualification and independent pose accuracy.** Set stable device IDs (currently empty), measured intrinsics/distortion/mounts, actual exposure/readout/timestamp corrections and uncertainty from residuals. Check cold start, USB reconnect, surveyed positions, motion and single-tag heavy tails. Compare fused and odometry-only performance, including heading. Qualify mechanically safe degraded-module driving separately from algebraic observability.
- [ ] **FIELD-5 — Real boot service and rollback.** Build/test on the deployment Mini, install and boot without login as the actual account, verify log permissions/realtime scheduling/descendant cleanup and exercise rollback plus activation. Linux systemd watchdog and macOS launchd are different: `KeepAlive` restarts exits but does not detect a hung launcher. Establish an accepted hung-supervisor recovery policy on the chosen host.
- [ ] **FIELD-6 — Remaining WPILib and platform coverage.** The enabled WPILib RoboRIO simulator is verified on macOS (WPILib 2026, Phoenix 26.3): `./sim.sh --headless --mode-schedule` drives teleop and autonomous through the real gateway, and every disable neutralizes. Remaining: drive-to-pose under WPILib (it publishes no pose truth, so autonomous DRIVE aborts), scripted joystick input for the headless RoboRIO stand-in, which macOS SDK GradleRIO requires, and `tools/setup.ps1` install mode on a clean Windows/WSL machine if Windows remains supported; `-Check` alone is not installation evidence.
