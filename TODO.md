# Competition-readiness backlog

Scope: the reusable FRC platform needed to build robot logic reliably: actuation safety, transport, runtime/API contracts, sensing, deployment and diagnostics. Game strategy, shot timing, mechanism coordination rules and additional autonomous routines are not readiness requirements here.

This is an **open-work list**, not a changelog. Completed work and its reasoning remain in `git log`. Remove an item only after its acceptance check passes; a passing existing suite does not close a newly identified coverage gap. Physical acceptance follows [docs/BRINGUP.md](docs/BRINGUP.md).

## Open software items

- [ ] **TIME-3 — Run the tick-time target-age acceptance on the bench.** `Target::get` now logs one READ record per `Target` per selecting `update()`, and `session_report` judges target age at the tick from it (required, at most 25 ms, worst `process:lane` named). Close after a bench session passes `session_report --strict` with real operator input (BENCH.md).
- [ ] **MAC-1 — Build and run the full suite on macOS.** The RTMS process-identity check has a macOS branch (`sysctl` `KERN_PROC_PID` start time in `talOS/rtms/rtms.cc`) and durable writes use `F_FULLFSYNC` (`talOS/process/durable_sync.h`); only the macOS CI job compiles them, and the Mac mini is the deployment host. Also confirm INC-3's restart latency there, and measure a Python node's spawn-to-registry-row time from a cold boot: its module imports run before it registers, against the 5 s startup grace (Linux: 152–169 ms cold, 77–82 ms warm for `pose_estimator`). `tools/mac_qualify.sh` runs the build, the suite and both measurements ([bring-up](docs/BRINGUP.md#network-and-mini-build)). Evidence for the first-exec cost: in Bazel's darwin sandbox on a development Mac the first exec of a freshly written stub script takes 95–106 ms, a re-exec 5–15 ms (the launcher_test describe-timeout case failed at HEAD with a 100 ms probe deadline); measure whether the deployment Mini pays a similar first-exec cost on a new bundle, since it lands in every node's first probe and spawn.

- [ ] **PLATFORM-1 — Decide the control and camera host from measurements.** Every open incident (INC-3, INC-5, INC-6) is macOS-only, and macOS cannot set a camera's exposure duration (`avfoundation_source.mm` applies only continuous auto exposure, so `exposure_ms` is ignored and arena auto exposure blurs tags in motion). Run MAC-1/FIELD-3 on the Mini; if per-node loop lateness does not hold a 5 ms period with margin, move control nodes (and capture, unless a UVC control path is added) to a Linux coprocessor. Accept on recorded lateness tails and a captured frame at the configured exposure.
- [ ] **API-4 — Confirm one framework image on Linux.** libtalos_node.so has a soname and links the framework whole; `cpp_node_test.test_production_load_order` loads a copied library the way a talos_bundle does. Verified on macOS only: close after Linux CI passes it. If clang sanitizer builds on Linux fail on `-z defs` in `talos_cc_shared_node` (undefined `__asan_*`), exclude the flag under the sanitizer configs.
- [ ] **LOG-2 — Measure log rotation on a 10-minute bench session.** Capped logs now keep their tail in rotating segments, shares are weighted by record rate, and a restart is guaranteed half its member's share. Run a 10-minute bench session with a small `[robot] log_max_bytes` and check with `session_report` that every node kept its last minutes and no control loop stalled at a rotation (BRINGUP.md line 20).
- [ ] **CI-1 — Confirm the sanitizer legs and the Studio bindings check in CI.** Local macOS evidence (Mac mini, 2026-11-10): no ASan, UBSan or TSan report anywhere in `//...`. The remaining macOS failures were platform cost, not races: one `fork()` takes about 30 ms under ASan and 375 ms under TSan (1.5 ms plain, `posix_spawn` 0.7–2.6 ms), so `launcher_test` and `supervision_test` now carry `no_macos_sanitizer` and the macOS legs filter it; the Linux legs still run them. Close after a green pushed run of all four legs and the bindings diff. If macOS sanitizer coverage of the launcher matters, the alternative is spawning children with `posix_spawn`, which needs a redesign of the guardian fork.
- [ ] **CI-2 — Confirm the soak job in CI.** Locally the 180 s soak passed with seed 0 and failed with seed 1: the launcher killed a 300 ms SIGSTOPped `hardware_node` as stalled because the bridge refreshed its heartbeat only every 250 ms. The bridge now refreshes it every 10 ms (`HardwareNode::RefreshLiveness`). Close after a green CI soak on both OSes; a new `hardware_node` stall kill there is a new cause, not this one. Do not widen any bound.
- [ ] **CAM-1 — Sim camera CPU budget on 3-vCPU CI.** Sim camera work (render, detection, solve, recording) is off the loop thread; a camera's `update()` only posts a capture request and collects at most one result. Revisit the sim camera CPU budget on 3-vCPU CI runners and the coprocessor (cameras per host, frame rate or resolution) from measured per-camera CPU, worker throughput (`frames_processed_count` vs `frames_captured_count`) and timer lateness; do not widen the stall limit. `simulation/accuracy.py` `camera_health_issues` (processed >= 95% of captured) now measures that worker throughput, so it can flag a loaded host.
- [ ] **SAFE-1 — Position control after a TalonFX reset on an un-homed motor.** `requires_zero` defaults to false, and `ForgetZeros` marks `zero_lost` only for rezeroed devices (`talOS/devices/devices.cc`), so a rotor-feedback position mechanism that never rezeroes re-bases silently when a brownout resets its TalonFX and is re-authorized after restore. Decide a fail-safe default (hold position and motion-magic neutral after any device reset until rezero or an explicit opt-out), with a SimHardware test of the reset case.
- [ ] **SAFE-4 — RoboRIO loop does synchronous logging.** The single RoboRIO loop thread, the only runtime enforcer of the command timeout and DIO/PWM neutral (`Gateway::Tick`), writes multi-line `std::cerr` reports on every motor FaultField change, feedback-validity change and apply failure (`PhoenixBackend.cpp`). Move logging off that thread (bounded queue, rate-limited) and record loop overruns; whether TalonFX and DIO go neutral if the loop hangs is a FIELD-2 measurement.
- [ ] **RT-1 — No memory locking on macOS.** `ConfigureRealtime` locks nothing on macOS (`mlockall` is ENOSYS) and shared-memory rings are not prefaulted, while ARCHITECTURE.md says loops run "with memory locked". Unprivileged `mlock` of heap and shared mappings works on the Mac mini: lock and prefault the rings, loop stacks and hot text, or correct the claim; measure major faults per node during a recorded match.
- [ ] **RT-2 — Realtime under launchd is unmeasured and its loss invisible.** The LaunchDaemon plist (`tools/deploy.sh`) sets no `ProcessType`, which launchd throttles; every measurement so far ran from a shell, and `restart_latency.py` runs `--sim` at timeshare. A refused realtime request prints one stderr line only. Set the process type, publish the scheduling outcome in the registry row, fail `session_report --strict` on it, and measure timer lateness under launchd (FIELD-3).
- [ ] **RT-3 — No priority ordering between loops.** On macOS `SetThreadPolicy` ignores `RealtimeOptions::priority`, so the bridge does not run above the nodes as `talOS/bridge/node.cc` claims; on Linux every node, including the Python pose estimator, telemetry and cameras, runs `SCHED_FIFO` 50. Give actuator owners and the bridge precedence over observers and measure `update()` p99/max per node on the Mini (including Python GC).
- [ ] **OBS-1 — Retention can delete a match.** Older sessions share half of `log_max_bytes`, removed oldest first by directory mtime (`talOS/launcher/launcher.h`), so one long pit session after a match can delete it within one or two boots. Prefer FMS-attached sessions (or a pinned marker) and measure per-match log size (LOG-2).
- [ ] **OBS-2 — Supervisor reasons are not in the session.** Stall and construction kills and crash/restart lines go to the launcher's stdout/stderr, discarded under launchd, and the manifest keeps only the last run's exit. Record every run's exit, signal and kill reason in the manifest.
- [ ] **OBS-3 — No code identity in a session.** The manifest carries only `config_sha256`, the bundle no git revision or binary digest, and the RoboRIO build is never recorded; after a rollback nobody can tell which build drove a match. Record both.
- [ ] **OBS-4 — A telemetry-node restart wipes Studio's history.** A new `stream_id` clears the store and the manifest baseline (`studio/src/worker.ts`, `studio/src/data/events.ts`), losing pre-crash plots and the restarts in that window. Keep history across a stream restart.
- [ ] **ARCH-1 — Split the header monoliths.** `talOS/launcher/launcher.h` (about 3,600 lines, `Run` about 365 and `Supervise` about 256 lines), `talOS/configuration/config_parser.h` and `talOS/introspection/registry.h` are header-only; `log_dump` includes the whole supervisor for `MergeLogs`. Split into `.cc`-backed libraries (spawn, child output, session, describe graph, supervisor, log merge).
- [ ] **ARCH-2 — Layering and RULES.md 2 are not enforced.** `talOS/node` reads `hardware::Config` timeouts through `talOS/configuration`, `talOS/devices` depends on `talOS/bridge`, every core library is public, and `LintGraph` skips role checks for the `hw` owner, so a node can publish `/hw/request/<self>` with a plain `Publisher`. Restrict visibility of the request packet and RTMS publishers, lint `/hw/request` writers, and fix or enforce the ARCHITECTURE.md layering sentence.
- [ ] **ARCH-3 — One definition of a target lane.** Lanes are recognised three ways (`naming::IsTargetLane`, the launcher's `find("/target/")`, `session_report.py`'s regex) and their path built in four places; `contract.bzl`'s `_check_topics` accepts names NAMING.md rejects; subsystem tables accept unknown keys (`[subsystems.arm.target]` silently uses the default policy). Use one grammar and builder, and refuse unknown keys.
- [ ] **CI-3 — CI checks only each push's diff.** Format, tidy and buildifier diff `github.event.before`, so a cancelled run's commits and a failed check are never checked again, and clang-tidy skips test code. Check the whole branch against the merge base on pull requests and on pushes to `main`. Also open: no full-graph or Python test runs under a sanitizer; the soak runs only seed 0 and never on `main`; `replay_inputs_test` lacks `no_macos_sanitizer` (fails 2 of 3 under macOS TSan for the fork-cost reason the others carry); `hardware_node_test`'s `TestPort()` reuses a closed ephemeral port; a macOS `field_graph_test` probe failed with `setpgid: Operation not permitted` (unexplained).
- [ ] **DEPLOY-1 — Mac mini boot and power.** Nothing covers 12 V power and brownout ride-through, `pmset autorestart`, sleep, automatic updates, or FileVault (which keeps the LaunchDaemon from starting until a login); `tools/mac_qualify.sh` only prints sleep settings. AVFoundation camera permission is an interactive prompt that cannot appear under a LaunchDaemon with nobody logged in. Decide with PLATFORM-1; if the Mini stays, configure and check these in `deploy.sh`/`mac_qualify.sh`.
- [ ] **DEPLOY-2 — The drive team cannot see the main processor.** The Driver Station shows green code and comms while the RoboRIO hears no companion commands or a mismatched protocol version (`Robot.cpp` reports neither), and the autonomous routine is chosen with no driver feedback. Report companion link loss and the selected routine to the Driver Station, and write a pre-match checklist.

## Unresolved incidents — investigate, do not declare fixed by a rerun

- [ ] **INC-2 — Confirm the Phoenix simulator stall fix in CI.** **Cause established.** Phoenix's desktop simulator serves every simulated device from one thread, which also rewrites each device's `ctre_sim/*.dat` in the working directory on every config write. While Gradle wrote the other build variant to the same disk, a rewrite blocked that thread for up to hundreds of milliseconds: configure requests failed (TxFailed/RxTimeout), feedback went stale and `Configure()` left devices unavailable (CI runs 42718398981, 42762211224, 42769978513, 42775301670). A disk write load reproduces this locally; the same load with that directory in RAM does not. `PhoenixBackend_test` now keeps simulator state in a fresh `/dev/shm` directory and bounds each wait for configured, fresh, neutral devices (`AwaitReady`, whose failure names each device and its state). Close once CI runs that include the fix pass the RIO adapter job; an `AwaitReady` failure there is a recurrence. Linux success does not establish macOS SDK/toolchain readiness. On macOS the Phoenix simulator thread also stalls without disk load when the host CPU is loaded: at load 10–44 on 12 cores the enabled sim showed 1–4 all-device feedback stalls per second (50–260 ms), and `phoenixTest` failed 4 of 8 runs with `ctre_sim` on disk and 6 of 8 on a RAM disk. A RAM directory does not fix macOS; treat macOS `phoenixTest` failures under load as this, and close INC-2 on Linux CI as stated.
- [ ] **INC-3 — Critical-node restart latency on macOS.** **Incident.** In the macOS rerun of CI run 42720554711 (job 129517143967), `match_rehearsal_test` failed: the SIGKILLed drivetrain restarted (restart_count 1) but sent no `/hw/request/drivetrain` within the 300 ms the driver stays frozen, so the stale-lane check had nothing to examine. Linux runs pass; the Linux per-stage SIGKILL-to-first-request breakdown is in [restart latency](talOS/launcher/README.md#restart-latency). The macOS cause is not established: the deployment host is a Mac mini, so measure those stages there, also while nodes write their event logs to the same disk (`tools/mac_qualify.sh` runs `//talOS/launcher:restart_latency` idle and with `--disk-load 8`), before widening the window; the frozen producer must stay below the 500 ms stall floor. A syscall shim on the Mac mini under 8 disk writers found three disk waits on that path. Two are addressed: the restarted node's event-log open and header write ran on its loop thread before the first tick (145–528 ms; now on the log writer thread), and the manifest writer's create in the session directory stalled the restart's directory reads and fork (7–160 ms; a supervision pass now posts its manifest after its restarts). Open: the killed node's reap (SIGKILL → `waitpid` up to 250–1254 ms under disk load). Syncing per chunk does not clearly fix it: a kill-and-reap A/B on the Mac mini under 8 disk writers, with a program mimicking `LogWriter` (4 × 256 KiB pool, 280 KiB/s, writer thread; 135 kills per policy over three runs, 1-minute load 1.5–5.5 with other builds at times), measured kills slower than 100 ms / 250 ms / max: once-a-second `fsync` (current) 24 / 10 / 579 ms; `fdatasync` after each chunk 15 / 7 / 660 ms (per run 7, 7, 1 against 9, 9, 6 slower than 100 ms, so run-to-run spread exceeds the gain); with 32 KiB writes 4 / 2 / 627 ms of 45 but a 6.6 s sync stall filled the pool and dropped records; per-chunk `fsync` 10 / 7 / 797 ms and `F_BARRIERFSYNC` 22 / 11 / 1097 ms of 45; `F_NOCACHE` 13 / 7 / 1269 ms of 45. Per-chunk sync removes the slow reaps of an idle writer holding dirty pages (max 484 ms → 9 ms) but a kill then waits for the sync or write in flight, which take a quarter to a third of the writer's time under that load (`sync_file_range` is Linux-only). Remaining fix: no file I/O in the node process (the launcher, or a log process the restart does not wait for, writes the node logs). Not closed by those two changes: rerun the macOS stages with them.
- [ ] **INC-5 — Confirm the cause of probes exiting 127 on macOS.** **Incident; cause probable, not confirmed.** macOS CI runs 42785663001 (`supervision_test`, `alpha`) and 42720554711 (`graph_test`, `front_left_camera`) failed a `--describe` probe with exit 127 and no message. The probable cause is the child's guardian fork refused with `EAGAIN` at the per-user process limit while the probes run in parallel (reproduced under `RLIMIT_NPROC`); that path then exited 127 silently. A probe now retries a fork refused with `EAGAIN` or `ENOMEM` until the describe deadline, and every other child failure names its step and errno. A probe that spawns only after a retry prints `[launcher] probe of <binary> spawned on attempt N (after <step>: <errno>)`. Confirm from a macOS CI log, either that line or a failed probe naming `fork (guardian)` or `fork` (with the process counts the build-macos failure step records), that the process limit is the cause; a probe failure naming another step, or an exit 127 without a named step, means it is not. Close after that confirmation; a passing rerun without the line is not evidence.
- [ ] **INC-6 — Hardware-request output gaps above 30 ms on macOS CI.** **Cause found; close after green macOS CI.** `startup_test` and `match_rehearsal_test` require recorded `/hw/request` (or bridge `/hw/command`) rows at most 30 ms apart inside checked windows; macOS CI runs 42775301670 (43.8 and 46.9 ms) and 42796457757 (39.5 and 38.7 ms) failed it. Cause: under `--sim` every node loop runs at timeshare priority, and the graph alone uses about 254% CPU median (463% p90), more than a 3-vCPU runner has; A/B runs on the Mac mini with three free cores failed 3 of 3 at timeshare and showed no gap over 15 ms in any run with `TALOS_REALTIME=1`. Fixed for the macOS sim tests (`startup_test`, `match_rehearsal_test`, `soak_test`), which now set `TALOS_REALTIME=1` and fail on `talos: realtime scheduling incomplete`. Close after green macOS CI; a gap there with realtime held is a new cause. Do not widen the 30 ms bound.

## Physical and deployment qualification gates

These are separate from software fixes, not evidence that a failure already exists. Agents must not change physical CAN IDs or set `commissioned = true`.

Use the one-Kraken bench ([docs/BENCH.md](docs/BENCH.md), config `bench/`) for link/stop/timing qualification before the robot exists; it cannot qualify a full CAN bus, cameras or the drivetrain. Run `session_report --strict` on bench sessions; `NOT MEASURED` is not a pass.

- [ ] **FIELD-1 — Network, electrical configuration and commissioning.** Verify coprocessor/RIO addressing, field bundle selection, CAN IDs, encoder offsets, inversion and controller limits against the real robot. A responsible human commissions only after restrained disabled/enable tests; update configuration golden checks alongside deliberate hardware changes.
- [ ] **FIELD-2 — Independent stop and fault measurements.** Measure DS disable/e-stop, companion stop/stall, Ethernet removal, RIO cold reboot, single Talon/CANcoder loss and total bus loss. Confirm affected-output/dependency isolation and safe fresh recovery. Measure voltage/current or independent motion/power evidence, not merely requested neutral or invalid feedback. Include PWM zero versus pulse-loss behavior and persisted-config boot restoration.
- [ ] **FIELD-3 — Full-bus load and realtime tails.** On the actual coprocessor/RIO, record CAN utilization, per-signal ages, hardware gaps, command latency, loop lateness, callback duration and watchdog crossings under intended load, Python GC, disabled neutral refresh and reset restoration. Qualify achieved signal rates rather than assuming the requested rates. Desktop measurements are not Mini acceptance evidence; callback duration differs from dispatch lateness.
- [ ] **FIELD-4 — Camera qualification and independent pose accuracy.** Set stable device IDs (currently empty), measured intrinsics/distortion/mounts, actual exposure/readout/timestamp corrections and uncertainty from residuals. Check cold start, USB reconnect, surveyed positions, motion and single-tag heavy tails. Compare fused and odometry-only performance, including heading. Qualify mechanically safe degraded-module driving separately from algebraic observability.
- [ ] **FIELD-5 — Real boot service and rollback.** Build/test on the deployment Mini, install and boot without login as the actual account, verify log permissions/realtime scheduling/descendant cleanup and exercise rollback plus activation. Linux systemd watchdog and macOS launchd are different: `KeepAlive` restarts exits but does not detect a hung launcher. Establish an accepted hung-supervisor recovery policy on the chosen host.
- [ ] **FIELD-6 — Remaining platform coverage.** The enabled WPILib RoboRIO simulator is verified headless on macOS (WPILib 2026, Phoenix 26.3): `./sim.sh --headless --mode-schedule ... --joystick-schedule ...` drives teleop from a scripted stick and runs autonomous to its pose, and every disable neutralizes. Remaining: `tools/setup.ps1` install mode on a clean Windows/WSL machine if Windows remains supported (`-Check` alone is not installation evidence), and which macOS SDK GradleRIO requires. Under WPILib, simulated cameras get no truth (only the physics sim gateway publishes `/sim/state`), so pose there is seed plus odometry; if camera coverage under WPILib is ever needed, a `field_truth` sim node integrating `/hw/state` is the option.
